## Решение

### Задание 10.1
История заказов и пользовательские сессии - данные, по которым не должно быть высоких требований по производительности, поскольку они редко изменяемы, либо не участвуют в основных операциях. Здесь Cassandra не требуется. 

Корзина, остатки товаров и активные заказы(не завершены и не отменены) требуют скорость обработки, т.к. напрямую участвуют в основных операциях и могут затрагивать сразу нескольких пользователей в одной операции. Здесь Cassandra желательна.

Для остатков важен строгий кворум.

Описания товаров не так критичны и редко изменяемы, здесь Cassandra не требуется

### Задание 10.2

При изменении количества нод в каждом случае будет минимум решафлинга благодаря использованию виртуальных нод в Cassandra. Выбор ключей позволит равномерно распределить данные по нодам.

carts
partition_key: (onwer_type, owner_id)
clustering_key: status, updated_at
почему: Пользователи будут работать только со своими корзинами, поэтому можно использовать user_id как partition key для равномерного распределения. 

```sql
CREATE TABLE carts (
    owner_id uuid,
    owner_type int, -- 0 - user, 1 - session 
    items map<uuid, int> -- <product_id, quantity>,
    status text,
    created_at timestamp,
    updated_at timestamp,
    expires_at timestamp,
    PRIMARY KEY ((owner_type, owner_id), status, updated_at)
)  WITH CLUSTERING ORDER BY (updated_at DESC);
```

products_remaining(product_id, geo, quantity, price)
partition_key: (geo, product_id)
почему: геораспределение эффективно разделит данные по зонам. Потенциально большие города могут вызвать горячие партиции, но их можно разделить по регионам как отдельные geo/склады.

```sql
CREATE TABLE products_remaining (
    product_id uuid,
    geo text,
    quantity int,
    price decimal,
    PRIMARY KEY ((geo, product_id))
);
```

orders
partition_key: (geo, user_id)
clustering_key: created_at
почему: Пользователи будут работать только со своими заказам, поэтому можно использовать user_id как partition key для равномерного распределения. 


```sql
CREATE TYPE order_item (
    product_id uuid,
    quantity int,
    price decimal,
    name text
);

CREATE TABLE orders (
    id uuid,
    client_id uuid,
    created_at timestamp,
    items: list<frozen<order_item>> -- Неизменяемо после оформления заказа
    status text,
    sum decimal,
    geo text,
    PRIMARY KEY ((geo, user_id), created_at)
) WITH CLUSTERING ORDER BY (created_at DESC);
```

### Задание 10.3
Для остатков стоит использовать hinted handoff и согласованность QUORUM(R+W>N), т.к. нам важна скорость ответа, а read repair будет создавать задержки.
Для корзины и заказов можно использовать LOCAL QUORUM(R+W>N) и hinted handoff, из-за сильной привязки к геозоне.

Anti-entropy repair можно производить периодически в техническое окно для исправления пропущенных расхождений.

## Описание задания
Во время «чёрной пятницы» интернет-магазин использовал MongoDB с **шардированием на основе диапазонов (Range-Based Sharding)**. При резком увеличении нагрузки (50 000 запросов/сек.) возникла **высокая задержка при масштабировании**:

При добавлении новых шардов MongoDB **полностью перераспределяла данные** между всеми узлами, что вызывало **просадку latency** в пик нагрузки, так как система тратила ресурсы на перемещение данных.

Руководство решило перейти на БД Cassandra, чтобы обеспечить:

- Высокую отказоустойчивость (leaderless‑репликация).
- Быстрое горизонтальное масштабирование без полного перераспределения данных.
- Равномерное распределение данных.
